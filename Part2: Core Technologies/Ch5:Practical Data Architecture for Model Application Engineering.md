> 本章导读**
> 
> 多数大模型项目第一次"翻车"，不是模型选错了，而是**数据先出了问题**：知识库文档格式混乱导致 RAG 答非所问；换了 Embedding 模型没有重新向量化，检索结果一夜之间全部变差；知识库明明已经更新，语义缓存却还在返回旧答案；会话状态只存在内存里，一次发布重启，长流程工单 Agent 的上下文全部丢失。
> 
> 这些事故的根因不在模型、不在提示词，而在**数据架构**——我们如何定义数据对象、如何让数据在系统中流动、把数据存在哪里、如何管理数据的全生命周期、如何在合规前提下使用数据。
> 
> 在模型应用工程（MAE）中，数据拥有三重身份：它是**系统的燃料**（模型的知识来源）、是**产品的血液**（每一次请求都在消费和产出数据）、也是**系统自我改进的信号**（反馈数据驱动知识库与提示词持续迭代）。本章将系统展开 Ch2 §3.2 的数据架构框架，为后续 RAG 系统工程化与 Agent 生产实践打下数据地基。

读完本章你将理解：

- 为什么模型应用工程必须把"数据"当作一等工程对象来管理；
- 模型应用系统中六类核心数据对象：知识、向量、会话、缓存、评测、观测配置；
- 四条关键数据流：RAG 数据流、会话数据流、缓存数据流、反馈回流数据流；
- 存储选型的决策框架：向量库、关系库、Redis、对象存储各自的适用边界；
- 数据生命周期管理：知识库版本与失效、缓存一致性、会话归档、Embedding 迁移、评测集迭代；
- 隐私、脱敏与合规：两层脱敏、检索权限、日志规范、数据出境与备案要点；
- 数据层典型技术债务与治理机制：反模式清单与质量监控。

> **前置知识回顾**
> 
> 1. 数据架构属于三层架构中的"数据层"，与应用架构、技术架构并列（Ch2 §3.2）；
> 2. 手段优先级中，RAG 上下文、数据增强、微调均以数据为前提（Ch2 §1.4）；
> 3. 评测集、BadCase 本质上也是数据对象，需要版本管理（Ch3 评估体系）；
> 4. 上下文工程中的语义缓存、会话状态，是数据架构在提示词侧的使用形态（Ch4 §5）；
> 5. 用户 Prompt 中往往携带个人信息，数据合规是横切约束，详细合规制度见安全章。

# 1. 为什么"数据架构"值得独立成章

## 1.1 模型应用系统的本质：一条"数据加工管线"

抛开模型的神秘感，一个模型应用系统的每一次请求，本质上都是在做**数据的输入、变换、输出与回流**：
```
用户输入 ──┐
检索知识 ──┼─→ Prompt 组装（上下文工程，Ch4）─→ 模型调用 ─→ 输出校验 ─→ 业务结果
工具返回 ──┘                                                    │
会话历史 ──┘                                                     ↓
                                                    反馈采集（点赞/点踩/纠错）
                                                          │
                                                          ↓
                                               BadCase 库 → 评测集 → 知识库/Prompt 迭代
```
传统软件系统中，数据是"业务记录"：订单、客户、库存，系统围绕 CRUD 组织。模型应用系统则完全不同，数据出现了三个新特征：
| 特征     | 传统系统       | 模型应用系统                   |
| ------ | ---------- | ------------------------ |
| 数据类型剧增 | 以结构化业务记录为主 | 非结构化文档、向量、会话、评测、Trace 并存 |
| 数据驱动方式 | 数据被"查询"    | 数据被"加工成上下文"送入模型，直接影响输出质量 |
| 数据的价值  | 记录业务事实     | 三重价值：运行燃料 + 质量反馈 + 迭代信号  |

>**核心认知转变**：传统数据工程问"数据怎么存、怎么查、怎么算"；模型应用的数据工程还要多问三个问题——**这段数据会被模型读到吗？读到后输出质量如何？输出结果如何回流改进系统？
## 1.2 数据层失守：五个真实事故复盘
用反例建立直觉，比直接讲理论更有效。以下是五个典型生产事故，全部根因在数据层：
### 1.2.1 事故一：文档每治理，“垃圾进，垃圾出”
| 项     | 内容                                                    |
| ----- | ----------------------------------------------------- |
| 症状    | RAG 助手回答"如何重置 VPN 密码"时，答非所问甚至引用无关内容                   |
| 排查    | Trace 显示检索到的 Top-3 片段根本不是答案所在段落                       |
| 根因    | 知识库直接灌入 PDF 扫描件 + 表格型 Word 文档，解析后文本乱序、表格被拦腰截断，分块切碎了语义 |
| 数据层教训 | 原始文档质量决定检索质量上限，**上游数据治理是 RAG 的第一道工序**（第6章展开）          |

### 1.2.2 事故二：换了Embedding模型，检索全部变差
| 项     | 内容                                              |
| ----- | ----------------------------------------------- |
| 症状    | 升级"更强的 Embedding 模型"后，知识问答准确率不升反降               |
| 排查    | 对比新旧向量发现，新模型向量空间与旧向量完全不兼容                       |
| 根因    | 只改了在线向量化代码，**离线库里的旧向量没有重新生成**，新旧向量混在一个索引中检索     |
| 数据层教训 | 向量与 Embedding 模型版本强绑定，换模型 = 全量重嵌入 + 版本切换，见 §5.4 |

### 1.2.3 事故三：知识已更新，答案还是旧的（毒缓存）
| 项     | 内容                                          |
| ----- | ------------------------------------------- |
| 症状    | 新发布的制度文档已经生效，助手仍回答旧制度内容                     |
| 排查    | 检索链路没问题，命中了**语义缓存**                         |
| 根因    | 语义缓存 key 只含用户问题向量，**未包含知识库版本号**；知识库更新后缓存未失效 |
| 数据层教训 | 缓存必须"版本感知"，缓存的是"过去的正确答案"，见 §5.2             |

### 1.2.4 事故四：一次发布，长流程 Agent 上下文全丢
| 项     | 内容                                                   |
| ----- | ---------------------------------------------------- |
| 症状    | 工单处理 Agent 在用户填完第 3 步后突然"失忆"，报错让用户重新开始               |
| 排查    | 应用发布重启后，会话状态丢失                                       |
| 根因    | 会话状态只存在进程内存 / 无持久化 Redis，重启即清空                       |
| 数据层教训 | 业务关键状态必须分层持久化：热状态可重建的放 Redis，不可丢失的落数据库，见 §2.3 与 §5.3 |
### 1.2.5 事故五：评测集被污染，指标虚高假象
| 项     | 内容                                    |
| ----- | ------------------------------------- |
| 症状    | 提示词优化后离线评测得分大涨，上线后真实体验没有变好            |
| 排查    | 审查评测集发现，开发人员把"新版本的正确回答"直接追加进评测集当标准答案  |
| 根因    | 评测集没有版本控制与变更评审，标准答案被"顺手"改写            |
| 数据层教训 | 评测数据是测试资产，**必须像代码一样受控**，见 §2.5 与 §5.5 |
>**共性问题**：五个事故没有一个需要"换更强的模型"解决，全部是数据对象定义不清、数据版本不可控、数据生命周期缺失导致的。这就是数据架构必须独立成章的原因——**它是模型应用工程最容易忽略、却最先爆发问题的一层**。
## 1.3 数据架构在全书知识网络中的位置
```
            Ch4 提示词与上下文工程
             （语义缓存 / 会话状态是数据对象）
                       │
Ch1 认知 ── Ch2 体系（§3.2 数据架构总览）── Ch5 数据架构实践（本章）
                       │                        ├─→ Ch6 RAG 系统工程化（消费知识/向量数据）
                       │                        ├─→ Ch7 Agent 生产实践（消费会话/状态数据）
                       │                        └─→ Ch3 评估体系（评测集/BadCase 是数据对象）
                       │
                  Ch8 安全与合规（隐私/出境/审计，本章 §6 给数据侧落地清单）
```
- **向前承接**：Ch2 §3.2 给出了数据架构的框架（对象、流、存储、生命周期、安全），本章把它展开为可落地的工程实践；
- **向后供给**：第6章 RAG 消费"知识 + 向量"两类数据，第7章 Agent 消费"会话 + 状态"数据——没有这章的地基，后续章节的很多手段无处安放；
- **横向咬合**：评估体系的评测集、BadCase 需要存储与版本管理；上下文工程的缓存与多轮对话管理本质是数据访问模式。

> **一句话定位**：本章是模型应用工程体系中的"数据总纲"，它不解决"怎么切分文档""怎么调检索"这类具体算法问题（那是 RAG 章的职责），而解决"数据从哪里来、存在哪、如何流动、如何保真、如何合规、如何治理"的系统性问题。
## 1.4 数据架构设计的五大原则
贯穿全章的五条原则，也是后续每一节展开的坐标：
| 原则       | 回答的核心问题                   | 违背时的典型表现                    | 关键手段                              |
| -------- | ------------------------- | --------------------------- | --------------------------------- |
| **可溯源**  | 模型说出的每句话，能否追到数据源头？        | 回答无法引用来源；出幻觉无法定位是哪份文档导致     | 文档/分块携带 ID 与来源元数据；Trace 记录检索片段 ID |
| **可版本**  | 数据变了，能否知道何时、为何、被谁改的？能否回滚？ | 换了 Embedding 静默失效；知识库更新无法回溯 | 文档级版本、向量索引版本、评测集版本、配置版本           |
| **可观测**  | 数据质量下降时，能否在用户投诉前发现？       | 摄入失败没人知道；缓存命中率异常没人看         | 数据质量指标 + 告警（§7.2）                 |
| **安全合规** | 敏感数据是否被越权检索/输出/留存？        | 文档越权检索；日志存了完整 Prompt        | 入库脱敏、检索权限过滤、日志最小化、审计（§6）          |
| **成本可控** | 存储与算力成本是否随数据膨胀失控？         | 全部数据放热存储；冷数据永不归档            | 冷热分层、TTL、归档生命周期（§5）               |

> **实践建议**：把五条原则当成数据架构评审的 Checklist。任何新增数据对象或数据流，过一遍五条原则：能不能溯源？要不要版本？可不可观测？敏不敏感？成本多少？——五问全过，再谈存储选型。

# 2.核心数据对象全景
一个模型应用系统涉及的数据对象远比传统系统复杂。先给全景，再逐个拆解。
| 大类    | 典型对象                    | 一句话职责             | 存储倾向            | 敏感等级       |
| ----- | ----------------------- | ----------------- | --------------- | ---------- |
| 知识数据  | 原始文档、分块片段、元数据           | 模型的知识来源（RAG 源）    | 对象存储 + 关系库（元数据） | 中-高（含企业知识） |
| 向量数据  | 文档向量、Query 向量、缓存向量      | 语义检索与语义缓存的数学载体    | 向量库 / Redis     | 中          |
| 会话与状态 | 对话历史、会话状态、业务参数          | 多轮交互与 Agent 流程的记忆 | Redis + 关系库     | 高（含用户输入原文） |
| 缓存数据  | 精确缓存、语义缓存               | 降本降延迟的答案复用        | Redis           | 中          |
| 评测数据  | 评测集、BadCase、红队样本        | 质量验证与迭代的测试资产      | Git/对象存储 + 关系库  | 中-高        |
| 观测与配置 | Trace 日志、Prompt 模板、审计日志 | 排障、追溯、审计          | 日志系统 + 关系库      | 高          |
>数据对象与上层章节的对应**：知识/向量数据对接第6章 RAG；会话/状态对接 Ch4 §5.4（多轮对话管理）与第7章 Agent；评测数据对接 Ch3（评估体系）；缓存数据对接 Ch4 §5.1（Token 成本控制）；观测配置对接 Ch2 §3.3（技术架构可观测性）。
## 2.1 知识数据：原始文档与分块片段

知识数据是 RAG 的源头，也是最需要"治理"而非"搬运"的数据。
### 2.1.1 原始文档（Document）
一份进入知识库的原始文档，必须携带完整的元数据才能被治理：
```json
{
  "document_id": "DOC-2026-0087",
  "title": "VPN 客户端安装与故障排查手册 v3.2",
  "source_system": "ITSM-Wiki",
  "owner_dept": "IT 服务台",
  "version": "3.2",
  "permission_domain": "internal-it",
  "doc_type": "manual",
  "author": "zhang.wei",
  "published_at": "2026-06-18",
  "content_hash": "sha256:9f2c...",
  "status": "published"
}
```
**为什么元数据不可或缺**：
| 能力   | 缺少元数据时的后果                 |
| ---- | ------------------------- |
| 溯源引用 | 回答无法给出"来自哪份文档"，幻觉无法定位     |
| 权限过滤 | 无法实现"不同用户检索不同范围"，可能越权     |
| 失效下架 | 文档更新/删除时，无法定位并清理它的所有分块与缓存 |
| 增量更新 | 无法判断哪些文档变了、哪些要重新分块向量化     |
| 质量分析 | 无法按来源、部门、类型统计回答质量差异       |

### 2.1.2 分块片段（Chunk）
文档经过切分后产生分块，分块是检索的最小单位：
```
chunk_id: DOC-2026-0087#C12        ← 可追溯到父文档
doc_id:   DOC-2026-0087
seq:      12                        ← 块在文档中的顺序
title:    "故障排查：证书过期处理"
content:  "…（正文片段）…"
token_count: 486
meta:     {section: "4.3", page: 12, permission_domain: "internal-it"}
```
>关键设计**：`chunk_id` 必须包含 `doc_id`，这是"按文档失效"（下架某文档 = 删除该 doc 全部 chunk）的基础。实践中大量系统只存了正文没有父子关系，导致文档更新时旧分块成为"幽灵数据"继续被检索。
## 2.2 向量数据：Embedding的三类角色
向量数据是模型应用独有的数据形态。同一个 Embedding 模型产出的向量，按用途分三类：
| 类型       | 谁生成          | 生命周期       | 规模      | 典型存储  | 失效条件              |
| -------- | ------------ | ---------- | ------- | ----- | ----------------- |
| 文档向量     | 离线管道，入库时批量生成 | 与文档生命周期一致  | 大（百万级+） | 向量库   | 文档更新/Embedding 换版 |
| Query 向量 | 在线请求，实时生成    | 即用即弃（毫秒级）  | 不落库     | 内存    | 请求结束              |
| 缓存向量     | 在线请求，写入缓存时生成 | 与缓存 TTL 一致 | 中       | Redis | TTL 过期/主动失效       |
向量记录必须携带版本信息**，这是事故二的解药：
```json
{
  "vector_id": "vec_9f2c...",
  "chunk_id": "DOC-2026-0087#C12",
  "embedding_model": "bge-m3",
  "embedding_version": "2026-05-01",
  "dimension": 1024,
  "created_at": "2026-06-19T08:00:00Z"
}
```
**向量是"黑盒"的数学对象**：相似度分数高 ≠ 语义一定正确。向量检索只能告诉你"这批候选与问题在向量空间上相近"，最终是否相关、是否可引用，必须结合元数据过滤与重排（第6章）。向量索引中混入不同模型的向量（维度相同但空间不同）是静默故障的经典来源。
## 2.3 会话与状态数据
会话数据记录"人和系统聊了什么、进行到哪一步"。它是多轮对话（Ch4 §5.4）与 Agent 流程（第7章）的记忆载体。
按"多热、多重要"把会话数据分三层：
| 层级  | 内容           | 存储          | 保留期    | 丢失容忍度              |
| --- | ------------ | ----------- | ------ | ------------------ |
| 热数据 | 进行中的会话消息、状态  | Redis（带持久化） | 数小时-数天 | 低（流程进行中）           |
| 温数据 | 近期会话完整记录     | 关系库         | 数周-数月  | 中                  |
| 冷数据 | 归档会话（审计/分析用） | 对象存储/数仓     | 数月-合规期 | 高（丢了也可接受？不，合规要求除外） |
会话状态对象示例（对接 Ch4 §5.4 的"显式状态追踪"）：
```json
{
  "session_id": "sess_8f21",
  "user_id": "u_1033",
  "topic": "VPN 连接故障",
  "state": {
    "user_system": "Windows 11",
    "troubleshooting_steps": ["证书检查-已排除", "网络配置检查-未解决"],
    "current_step": "need_diag",
    "ticket_id": "TKT-2026-5512"
  },
  "updated_at": "2026-09-04T10:00:00Z"
}
```
>实践建议**：能重建的状态（如从对话历史可以推导）可以放宽持久化要求；不能丢失的业务状态（如工单号、审批结果、扣费动作）必须落数据库，且更新与业务动作要保证顺序一致（先落库成功，再返回"成功"给用户）。这是第7章 Agent 状态管理的核心约束。
## 2.4 缓存数据：精确缓存与语义缓存
缓存是大模型应用成本治理的第一杠杆（相同问题反复调用模型 = 双倍成本双倍延迟）。缓存数据分两类：
| 类型   | 命中条件       | 典型实现             | 省成本幅度      | 风险           |
| ---- | ---------- | ---------------- | ---------- | ------------ |
| 精确缓存 | key 完全一致   | `hash(用户+问题+版本)` | 高（完全重复的问题） | 低            |
| 语义缓存 | 语义相似度 ≥ 阈值 | Query 向量检索缓存向量   | 高（相似问题可复用） | **高（误命中风险）** |
**语义缓存的危险在于"缓存的是过去的正确答案"**：知识库更新、模型换版、Prompt 变更后，缓存答案可能已经过时甚至错误，却因为向量相似仍然命中。因此缓存 key 必须包含版本信息：
```
cache_key = hash(prompt_version + model_version + kb_version + query_normalized)
```
## 2.5 评测数据：评测集、BadCase 与红队样本
评估体系（Ch3）的产出物，本质上是模型应用最宝贵的测试资产。数据架构必须给它一个"家"。
**评测数据的构成**：
| 类型         | 内容               | 来源             | 管理要求      |
| ---------- | ---------------- | -------------- | --------- |
| 标准评测样本     | 输入 + 参考答案 + 维度标注 | 专家编写、线上回流      | 版本管理，变更评审 |
| 边界 Case    | 易错、模棱两可的输入       | 专家构造           | 持续补充      |
| 负向对抗样本     | 恶意 Prompt、越权请求   | 红队测试           | 定期更新攻击模式  |
| 历史 BadCase | 线上翻车案例           | 反馈回流（Ch3 §4.3） | 评审后入库     |
单个评测样本的数据结构：
```json
{
  "case_id": "EVAL-2026-0042",
  "category": "boundary",
  "input": "VPN 连不上，但我用的是公司发的 MAC 电脑",
  "ground_truth": "应引导检查 macOS 证书信任链…",
  "eval_dimensions": ["factual_consistency", "relevance", "completeness"],
  "source": "badcase-回流-2026-08",
  "created_at": "2026-08-12",
  "dataset_version": "eval-set-v2.3"
}
```
>⚠️ **评测集污染的两种隐蔽方式**：(1) 开发人员把新版本的正确输出直接追加为标准答案（指标虚高，事故五）；(2) 评测样本与知识库"同步更新"，知识改了标准答案跟着改，回归测试失去意义。评测集变更必须走评审，与业务版本解耦。
## 2.6 观测数据与配置元数据
最后一类数据不直接参与业务，却决定系统"能不能被运维、被追溯"。
| 子类        | 内容                                  | 价值                | 特点              |
| --------- | ----------------------------------- | ----------------- | --------------- |
| Trace 日志  | 每次请求：入参、出参、检索 doc/chunk ID、模型、耗时、成本 | 排障、质量分析、幻觉溯源      | 量最大、价值密度低、含敏感内容 |
| Prompt 配置 | Prompt 模板、版本、变量定义                   | 提示词工程资产（Ch4 §6.1） | 量小、价值高、变更需审批    |
| 审计日志      | 谁在何时访问/修改了什么数据                      | 合规、安全追溯           | 只增不改、防篡改        |
| 业务指标      | 缓存命中率、召回率、成本等                       | 运营监控              | 聚合后存储           |
>**三类数据的治理差异**：观测数据量大、留短（脱敏后保留 30-90 天）；配置数据量小、留长、走变更审批；审计数据只增不改、按合规期留存（见 §6）。把三类数据混在一个表里是常见的治理混乱。
# 3. 数据流：数据如何穿越系统
数据对象是"名词"，数据流是"动词"。模型应用系统有四条关键数据流，其中前三条是"运行动脉"，第四条是 MAE 独有的"学习回路"。
```
① RAG 数据流：源文档 ─→ 摄入 ─→ 向量化 ─→ 检索 ─→ 生成      （知识供给）
② 会话数据流：用户输入 ─→ 状态读写 ─→ 模型调用 ─→ 返回 ─→ 落库 （交互记忆）
③ 缓存数据流：请求 ─→ 命中? ─→ 返回 / 未命中→调用→写入       （成本与延迟）
④ 反馈回流流：用户反馈 ─→ 采样 ─→ 标注 ─→ BadCase ─→ 改进    （自我进化，Ch3 §4.3）
```
## 3.1 RAG 数据流：离线写、在线读，双管线分离
RAG 数据流必须拆成两条管线，这是生产级 RAG 的第一原则（第6章还会深化）：
```
【离线数据管线】（写路径，批处理，异步）
源系统文档 → 拉取/同步 → 解析清洗 → 分块 → 元数据抽取 → Embedding
   → 写入（文档库 + 向量库）→ 索引版本号 +1 → 发布为"当前版本"
                    ↑ 全程不经过用户请求链路

【在线数据管线】（读路径，实时，同步）
用户 Query → 向量化 → 检索（向量 + 元数据/权限过滤）→ 重排 → 上下文组装
   → 送入模型（Ch4 §5 上下文工程）→ 输出 → 校验 → 返回
                    ↑ 只读"已发布版本"的索引
```
**设计要点**：
| 要点    | 说明                                 |
| ----- | ---------------------------------- |
| 读写解耦  | 离线管道再慢不影响在线请求；在线管道绝不直接写库           |
| 版本发布  | 离线产物带索引版本号，发布是"指针切换"，可秒级回滚         |
| 增量优先  | 用变更事件（文档增改删）驱动增量处理，定期全量兜底校准        |
| 一致性窗口 | 从文档变更到检索生效存在延迟，需在知识库元数据中记录"最后同步时间" |
>**与 RAG 章的衔接**：本章负责"数据流的两条管线与版本机制"骨架；分块策略、Embedding 选型评估、重排算法等细节在第6章展开。写路径质量决定读路径效果——**文档摄入时的清洗与元数据工作，远比上线后调 top-k 更重要**。
## 3.2 会话数据流：先读后写，状态与动作一致
会话数据流的难点不在"存"，而在**读写时序与一致性**：
```
用户输入
  → 1. 会话服务读取会话状态（Redis/DB）     [读]
  → 2. 组装上下文：历史摘要 + 状态 + 业务参数（Ch4 §5.4）
  → 3. 调用模型 / 工具执行
  → 4. 输出校验（Ch4 §4.4）
  → 5. 更新会话状态与消息记录               [写：先落库]
  → 6. 返回结果给用户                       [后应答]
        ↓（异步）
  → 7. 反馈埋点 / Trace 上报 / 采样回流       [与响应解耦]
```
两条铁律**：

1. **先写后答**：状态更新先落库成功，再向用户返回"已完成"。否则用户看到成功、状态却丢了（事故四）。
2. **重试幂等**：模型调用与业务动作重试时不能重复执行副作用（重复建工单、重复扣费）。重试请求携带 `request_id`，服务端按幂等键去重。模型调用天然非幂等（Ch2 §1.4），业务动作层必须兜底。

> **与 Agent 章衔接**：多步 Agent 的每一步都是"读状态 → 决策 → 动作 → 更新状态"的循环。状态存储设计（§2.3）与读写一致性是第7章 Harness 中状态管理组件的落地基础。
## 3.3 缓存数据流：先校验、后缓存
```
请求进入
  → 计算 cache_key（含 prompt/model/kb 版本，§2.4）
  → 精确缓存命中? ──是──→ 返回缓存结果（校验 TTL 与版本）
        │否
  → 语义缓存检索（Query 向量 vs 缓存向量，阈值≥0.92 需实测校准）
        │命中 → 返回；未命中 ↓
  → 调用模型
  → 输出校验（格式/Schema/业务，Ch4 §4.4）
        │未通过 → 不入缓存，走降级/修复
        │通过 ↓
  → 写入缓存（TTL）→ 返回
```
**要点：**
| 要点     | 说明                                         |
| ------ | ------------------------------------------ |
| 版本感知   | cache_key 绑定 Prompt/模型/知识库三版本，任一升级自动"逻辑失效" |
| 先校验后缓存 | 只缓存通过校验的输出，防止错误/违规/注入答案被长期复用               |
| TTL 分层 | 高时效知识短 TTL（分钟-小时），稳定知识长 TTL（天级）            |
| 敏感不缓存  | 涉及 PII、机密内容的问答建议不缓存或极短 TTL，降低泄露面           |
| 主动失效   | 知识库发布事件触发按 doc 前缀清理相关缓存（对接 §5.1 文档状态机）     |

## 3.4 反馈回流数据流：MAE 的自我进化回路

第四条流是第四阶段范式的核心（Ch3 §4），也是数据架构最容易被忽视的职责——**把线上运行数据变成系统的改进信号**：
```
用户反馈（点赞/点踩/纠错/重新提问）
  → 埋点事件管道（异步，MQ）
  → 采样策略（低风险 1-5%，高风险 10-20%，异常 100%，Ch3 §4.2）
  → 质量标注（规则 + AI-Judge + 人工，Ch3 §3）
  → 判定为 BadCase？
      ├─ 否 → 归入"可接受样本"池（用于统计分布）
      └─ 是 → 写入 BadCase 库（评审后）
            → 定期分析（聚类根因）
            → 触发改进动作（优先级从低到高）：
               ① 补充/修正评测集（防回归）      ← 成本最低，先做
               ② 修正知识库文档（改源头）
               ③ 调整提示词/分块/检索参数
               ④ 沉淀微调数据集（成本最高，后置）
            → 新版本经评估门禁后发布（Ch3 §5.1 CI 流水线）
```
>**数据架构在这条流上的责任**：把"反馈埋点 → 事件管道 → BadCase 库 → 评测集更新"的存储与管道建好。管道断了，再好的评估方法论也收不到数据。这条回流链路同时也是评测集活水（§5.5）与知识库迭代（§5.1）的入口。
## 3.5 四条数据流的共性设计约束
| 约束     | 含义                      | 违反时的症状       |
| ------ | ----------------------- | ------------ |
| 异步解耦   | 写路径（摄入、反馈）不阻塞用户请求       | 一次知识更新拖垮在线服务 |
| 幂等     | 重试不产生重复副作用              | 重复建工单、重复写消息  |
| 可追踪    | request_id 贯穿全链路 + 数据血缘 | 无法定位幻觉来自哪份文档 |
| 版本感知   | 读路径只读已发布版本              | 新旧数据混用导致结果漂移 |
| 读多写少分离 | 在线检索与离线写入资源隔离           | 批量摄入挤占在线检索资源 |
# 4. 存储选型指南

## 4.1 选型的决策框架：按数据特征选，不按工具名气选

"网上都说向量库好，就把所有数据都塞进向量库"是数据层最大的反模式。正确的选型顺序是：**先分析数据特征，再匹配存储能力**。

**决策因素**：
| 决策因素   | 要问的问题                  | 影响                  |
| ------ | ---------------------- | ------------------- |
| 数据形态   | 结构化？非结构化文本？向量？文件？      | 决定存储大类              |
| 访问模式   | 点查？范围查询？相似度检索？复杂 join？ | 决定是否适合关系库/向量库       |
| 一致性要求  | 能否容忍秒级延迟一致？需要事务吗？      | 决定用 DB 还是缓存         |
| 规模与增速  | 数据量级、日增量？              | 决定是否需要专用向量库         |
| TTL 特性 | 数据是临时的还是永久的？           | 决定是否用 Redis         |
| 敏感度    | 含 PII/机密吗？             | 决定是否需要额外加密/权限/隔离    |
| 运维成本   | 团队能运维几个存储组件？           | 决定组件数量（每多一个组件多一份成本） |

**推荐映射**（以企业 IT 运维助手场景为例）：
| 数据对象           | 首选存储             | 备选                     | 不建议               |
| -------------- | ---------------- | ---------------------- | ----------------- |
| 原始文档/附件        | 对象存储             | 文件服务器                  | 关系库（大字段）、向量库      |
| 文档元数据/分块元数据    | 关系库              | —                      | 向量库（复杂条件查询弱）      |
| 文档/分块向量（万-千万级） | 向量库（按规模选型）       | Redis 向量/PGVector（小规模） | 关系库做暴力相似度         |
| 会话热状态          | Redis（持久化开启）     | —                      | 纯进程内存             |
| 会话完整记录         | 关系库              | 数仓                     | Redis（无复杂分析）      |
| 缓存（精确/语义）      | Redis            | 内存缓存                   | 关系库（延迟高）          |
| 评测集/BadCase    | Git（版本）+ 关系库（标注） | 对象存储                   | 散落在 Excel/个人电脑    |
| Trace/日志       | 日志系统（ES/Loki 等）  | 对象存储归档                 | 关系库（量太大）          |
| Prompt 配置      | Git + 配置中心/关系库   | —                      | 硬编码在代码里（Ch4 §6.1） |
>**设计原则**：宁可"一个数据多种用途放多个位置"，也不要"一个库装所有"。同一份文档，原文在对象存储、分块在向量库、元数据在关系库，通过 `document_id` 关联——这是正常的，不是冗余浪费。
## 4.2 向量数据库：从“能用”到“够用”
向量库解决的是**语义相似度近邻检索**这一件事。围绕这一件事，按规模阶梯选型：
| 规模                 | 建议方案                            | 理由                   | 示例         |
| ------------------ | ------------------------------- | -------------------- | ---------- |
| 极小型（<10 万向量）       | Redis 向量检索 / 内存                 | 复用已有组件，不新增运维负担       | PoC、部门级小助手 |
| 小-中型（10万-500万）     | PGVector / Elasticsearch kNN    | 与现有数据栈融合，支持 SQL/倒排混合 | 单业务知识库     |
| 中-大型（>500万 或高 QPS） | 专用向量库（Milvus/Qdrant/Weaviate 等） | 分片、高并发、标量过滤性能        | 企业级多业务共享   |
| 托管诉求               | 云托管向量库（如云厂商向量服务）                | 免运维                  | 无专职运维团队    |
**生产选型维度对比**：
| 维度      | 关注点                                                    |
| ------- | ------------------------------------------------------ |
| 元数据过滤   | 能否在检索时下推 `permission_domain`、`doc_type` 等标量过滤（权限过滤的基础） |
| 混合检索    | 是否支持向量 + 关键词（BM25）混合召回（RAG 精度关键，第6章）                   |
| QPS 与延迟 | 峰值 QPS 下的 p95 延迟                                       |
| 一致性     | 写入后多久可见（影响增量更新延迟）                                      |
| 运维复杂度   | 分片/副本/备份/升级是否可控                                        |
| 成本      | 内存占用（HNSW 等索引吃内存）、存储成本                                 |

**什么时候根本不需要向量库**：

- 知识总量小到可以直接放进 Prompt 上下文（如内部几十页规章制度）；
- 业务是明确的关键词检索（型号、编号、代码），没有语义需求，用 Elasticsearch/数据库 LIKE/BM25 更可控；
- 团队没有向量库运维能力，且规模很小——先用 Redis/PGVector 起步，演进式扩容（呼应 Ch2 §1.4 演进式架构）。

>⚠️ **两个高频误区**：
>
>1. **把向量库当"万能数据库"**：向量库不擅长精确条件查询、事务、复杂聚合，业务元数据的权威存储应该在关系库；
>2. **向量库不等于权限系统**：ACL 必须由应用层在检索时通过元数据过滤下推（`WHERE permission_domain IN (…)`），而不是"先检索回来再过滤"——后者既低效又可能泄露。
## 4.3 关系型数据库：业务事实与元数据的"权威源"

关系库在模型应用系统中承担"事实与元数据的权威源"角色：
| 用途       | 典型表/对象          | 特点                |
| -------- | --------------- | ----------------- |
| 业务实体     | 用户、工单、审批流       | 事务强一致，需要 ACID     |
| 会话记录     | 会话表、消息表         | 结构化查询 + 关联业务      |
| 文档/分块元数据 | 文档表、分块表         | 权威元数据（向量库只存向量的索引） |
| 评测数据     | 评测样本表、标注表、运行结果表 | 关联查询、统计分析         |
| 审计元数据    | 审计日志表           | 只增、按时间分表/归档       |

>**核心原则**：元数据以关系库为权威源，向量库是它的"语义索引"**。文档在关系库中 `status=published`，向量库中的向量才有资格被检索；关系库删除文档 → 触发向量清理。谁先谁后、如何保证一致，见 §5.1 的"文档状态机"。
## 4.4 Redis / KV：缓存与热状态
Redis 解决"要快、要临时"的问题，不是"要可靠、要分析"的问题。
| 用途    | 数据结构             | 说明                      |
| ----- | ---------------- | ----------------------- |
| 精确缓存  | String + TTL     | `cache_key → 答案`，TTL 控制 |
| 语义缓存  | 向量检索（Redis 向量扩展） | 小规模语义缓存够用               |
| 会话热状态 | Hash/JSON + TTL  | 进行中会话，需开启 AOF 持久化       |
| 限流/计数 | 计数器              | 令牌桶、滑动窗口                |
| 分布式锁  | SETNX            | 防止摄入/发布并发重复执行           |
>⚠️ **Redis 的数据丢失权衡**：Redis 默认是内存数据库，RDB 快照可能丢最近数据，AOF 也可能丢最后 1 秒。**可重建的缓存丢一点没关系；不可重建的会话状态必须：(1) 开启 AOF everysec，或 (2) 关键状态同步写关系库**。事故四的教训就
>是"把不能丢的状态放进了能丢的存储"。
## 4.5 对象存储：非结构化数据的归宿

| 用途  | 说明  |
| --- | --- |
| 原始文档 | 知识库源文件（Word/PDF 等），配合元数据表 |
| 大附件/图片 | 工单附件、上传图片 |
| 日志与向量归档 | 冷数据、批量导出文件 |
| 模型评测产物 | 大规模评测样本集、结果快照 |

对象存储的关键能力是**生命周期规则**：自动将 30 天前的对象转冷、1 年后的删除（对接 §5.3 归档策略），无需人工干预。

## 4.6 存储选型避坑清单

| #   | 避坑点 | 危害  | 正确做法 |
| --- | --- | --- | --- |
| 1   | 所有数据全塞向量库 | 复杂查询痛苦、成本失控、事务缺失 | 按数据特征分流（§4.1 映射表） |
| 2   | 向量库当关系库用 | 权限、统计、join 全都别扭 | 元数据权威源放关系库 |
| 3   | 大文件塞关系库/Redis | 性能劣化、内存爆炸 | 对象存储 + 元数据表引用 |
| 4   | 缓存不设 TTL | 内存无限增长 + 数据永旧 | 版本感知 TTL（§5.2） |
| 5   | 环境不隔离，测试写生产 | 测试数据污染生产知识库 | 开发/测试/生产数据物理或逻辑隔离 |
| 6   | 多一个组件不加评估 | 存储组件数量失控 | 每个新增存储走选型评审 |
