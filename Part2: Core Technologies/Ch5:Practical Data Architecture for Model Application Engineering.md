> 本章导读**
> 
> 多数大模型项目第一次"翻车"，不是模型选错了，而是**数据先出了问题**：知识库文档格式混乱导致 RAG 答非所问；换了 Embedding 模型没有重新向量化，检索结果一夜之间全部变差；知识库明明已经更新，语义缓存却还在返回旧答案；会话状态只存在内存里，一次发布重启，长流程工单 Agent 的上下文全部丢失。
> 
> 这些事故的根因不在模型、不在提示词，而在**数据架构**——我们如何定义数据对象、如何让数据在系统中流动、把数据存在哪里、如何管理数据的全生命周期、如何在合规前提下使用数据。
> 
> 在模型应用工程（MAE）中，数据拥有三重身份：它是**系统的燃料**（模型的知识来源）、是**产品的血液**（每一次请求都在消费和产出数据）、也是**系统自我改进的信号**（反馈数据驱动知识库与提示词持续迭代）。本章将系统展开 Ch2 §3.2 的数据架构框架，为后续 RAG 系统工程化与 Agent 生产实践打下数据地基。

读完本章你将理解：

- 为什么模型应用工程必须把"数据"当作一等工程对象来管理；
- 模型应用系统中六类核心数据对象：知识、向量、会话、缓存、评测、观测配置；
- 四条关键数据流：RAG 数据流、会话数据流、缓存数据流、反馈回流数据流；
- 存储选型的决策框架：向量库、关系库、Redis、对象存储各自的适用边界；
- 数据生命周期管理：知识库版本与失效、缓存一致性、会话归档、Embedding 迁移、评测集迭代；
- 隐私、脱敏与合规：两层脱敏、检索权限、日志规范、数据出境与备案要点；
- 数据层典型技术债务与治理机制：反模式清单与质量监控。

> **前置知识回顾**
> 
> 1. 数据架构属于三层架构中的"数据层"，与应用架构、技术架构并列（Ch2 §3.2）；
> 2. 手段优先级中，RAG 上下文、数据增强、微调均以数据为前提（Ch2 §1.4）；
> 3. 评测集、BadCase 本质上也是数据对象，需要版本管理（Ch3 评估体系）；
> 4. 上下文工程中的语义缓存、会话状态，是数据架构在提示词侧的使用形态（Ch4 §5）；
> 5. 用户 Prompt 中往往携带个人信息，数据合规是横切约束，详细合规制度见安全章。
