> **本章导读**
传统软件依靠单元测试、准确率、回归测试保障系统质量。但大模型属于**概率开放式输出系统**：同样输入，模型可能返回不一样的回答；不存在绝对标准答案；公开Benchmark高分，不等于业务场景可用。
在模型应用工程第四阶段范式中，**评估不再是上线前的收尾工作，而是一等公民，贯穿需求、POC、准生产、上线运营全生命周期**。评估的产出直接驱动提示词修改、知识库迭代、Harness约束调整、数据集优化。

在投入时间、资金和资源构建应用之前，明确如何对其进行评估至关重要。这种方法称为评估驱动开发。这一名称的灵感源自软件工程中的测试驱动开发，即在编写代码之前先编写测试的方法。在AI工程中，评估驱动开发意味着在构建之前就定义好评估标准。
读完本章你将理解：
- 为什么传统测试手段在大模型面前失效；
- 如何搭建离线评测集；
- AI‑as‑Judge裁判模型的用法与陷阱；
- 如何构建线上业务反馈闭环；
- 如何搭建可自动化运行的评估流水线。

> 前置知识回顾
> 1. 模型输出属于概率开放式输出，传统二元对错判断不再适用
> 2. 项目环境分级：PoC原型、准生产、大规模生产
> 3. 反馈闭环是第四代模型应用工程的核心支柱

# 1为什么传统软件测试对大模型系统失效
传统软件逻辑是确定性的：相同输入，得到固定输出。我们可以写单元测试，断言输出等于预期值，用准确率、召回率完成质量校验。这套体系在传统机器学习阶段（分类、实体抽取等封闭集合输出）依然有效，但面对生成式大模型会遇到根本性障碍。

## 1.1 概率开放式输出：没有唯一标准答案
大模型生成回答属于开放式生成，同一个业务问题，**多个回答都可以是“正确”**。
> 示例：提问“简述模型应用工程是什么？

> 第一次提问某包回答：**模型应用工程，是面向已有的基础大模型，把模型能力转化为可上线、稳定可用的业务系统的一套工程方法论与实践体系，核心不是训练大模型，而是用好大模型做落地交付。**
>1. **定位区别**：和做预训练、训练大模型的「模型研发工程」不同；也不等同 LLMOps 运维，它覆盖从需求建模、应用构建到上线运维全流程，聚焦**“模型 + 业务系统” 混合软件的工程实现**。
>2. **核心工作**：把业务需求翻译为 AI 任务；做 Prompt、RAG、Agent 工作流编排；对接企业数据、工具接口；做效果评估、幻觉与风险约束；完成部署、可观测、成本与性能调优、迭代治理。
>3. **解决痛点**：解决 Demo 可用、生产不可靠；模型输出概率化、易幻觉；业务对齐差、难以规模化维护等落地问题，实现从原型到生产级 AI 应用的工业化交付。
>4. **关键特征**：是**确定性代码 + 非确定性大模型**的混合系统工程，强调约束、校验、兜底、可观测，而不是单纯依赖模型本身能力。
> 一句话浓缩：**模型应用工程，就是工程化地组装、驾驭现有大模型，去解决真实业务问题，产出稳定、可控、可运维的 AI 产品**。
>
>第二次提问某包回答：模型应用工程，属于**AI 工程（AI Engineering）**的分支，聚焦**不从零训练基础大模型，复用已有基座模型**，把模型能力转化为稳定、可上线、可规模化的业务应用的整套工程方法论与实践体系。
>核心目标：解决 Demo 效果好、生产环境不可靠的痛点，驯服模型的概率性、幻觉等固有缺陷，实现业务价值落地，而不是研究模型本身的预训练算法。
>主要工作内容：
>1. **能力组装**：Prompt 工程、RAG 检索增强、Agent / 工具调用、多智能体编排，把模型和业务数据、外部系统打通。
>2. **约束与管控（Harness Engineering）**：增加校验、兜底逻辑、权限边界，用规则约束模型行为，降低幻觉与错误输出风险。
>3. **系统工程**：架构设计、推理服务、降本提速、接口封装、版本管理。
>4. **评估与运维**：业务效果评测、链路可观测、监控告警、安全治理、持续迭代优化。
>和 MLOps 区别：MLOps 侧重**模型训练‑部署全生命周期**；模型应用工程重心在**模型之上的应用层开发、编排、治理**，微调只是可选手段，核心是应用系统本身。
> 一句话概括：**模型应用工程，是把现成大模型 “拼装成靠谱业务系统” 的工程学科，重点管应用，而非造模型**。

可以有多种措辞不同，但业务上全部合格的答案。无法简单使用 `assert(answer == expected_text)` 做单元断言。

同时即使关闭随机性`temperature=0`，基座版本升级、权重微调也会带来**模型行为漂移**，过去通过的测试用例新版本可能失效。

## 1.2质量是程度性，而非二元对错
大模型输出质量不是“对 / 错”，而是程度维度：事实准确性、相关性、完整性、格式合规、安全性、简洁度。
- ❌传统思维：回答正确 / 回答错误
- ✅模型应用工程思维：回答在多大程度上满足业务约束，存在哪些缺陷，缺陷是否可接受。

幻觉问题尤其典型：回答大部分内容通顺，但某一处细节编造虚构。整体文本看起来没问题，但局部事实错误。HTTP状态码返回200 OK，业务结果却是错误，这类**软故障无法被传统接口测试捕获**。

## 1.3 公开Benchmark ≠ 业务场景可用
很多团队直接拿MMLU、GSM8K等公开榜单评测结果当做业务质量依据，这是典型误区。MMLU、GSM8K定位：大模型经典评测数据集，分别侧重**通用知识多任务**、**数学推理**，是LLM能力测试最常用的两套基准。
### 1.3.1MMLU（Massive Multitask Language Understanding）大规模多任务语言理解
1. 核心定位
   
衡量大模型**通识知识、多领域理解、泛化能力**，考察模型是否具备人类的基础学科知识，属于多选问答评测。

2. 数据集概况
- 任务：**选择题（4选1）**
- 涵盖57个不同学科领域，分为4大类
  1. 人文社科：历史、法律、哲学、心理学
  2. 理工科学：物理、化学、生物、计算机
  3. 商业经济：经济学、管理学
  4. 其他：医学、社会学等
- 划分：`dev开发集`、`val验证集`、`test测试集`；**test集不公开答案**，用于排行榜打分。
- 输入形式：问题 + 4个选项，输出选出正确选项。

3. 评测范式
 - **Zero‑shot零样本**：不给示例，直接做题
 - **Few‑shot少样本**：prompt内给5道示例再做题（行业标准，MMLU主流报告都用5‑shot）

4. 能力指向
   
✅ 考察：知识记忆、阅读理解、学科推理、区分干扰选项

❌ 短板：不擅长复杂多步计算，不侧重逻辑推演，偏向“知识答题”

> 小提示：MMLU分数高 ≠ 模型会做复杂推理，仅代表**知识面广、基础学科答题能力强**。很多模型MMLU很高，但数学推理依然拉胯。

### 1.3.2GSM8K（Grade‑School Math 8K）小学数学推理数据集
1. 核心定位
专门测试**多步链式数学推理能力**，小学应用题，重点看模型能不能一步步思考解题，不是单纯背公式。

2. 数据集概况
   - 一共约8500道小学数学应用题
   - 题型：文字应用题，需要多步加减乘除运算，不是直接套公式
   - 每道题附带完整**推理步骤+最终答案**
   - 划分：train训练集，test测试集

3. 评测范式
   - Standard：直接输出答案
   - CoT（Chain‑of‑Thought思维链）：提示模型`Let's think step by step`，让模型先输出推理过程，再输出答案，**GSM8K使用CoT效果提升非常明显**。

4. 能力指向
   
✅ 考察：分步逻辑、因果推理、从自然语言提取数学条件、多步演算

❌ 短板：只是小学难度，不代表高等数学能力；容易出现计算幻觉，步骤对但算错数字。

> 教程小提示：GSM8K看的不只是最终答案正确率，更要看**推理链条是否合理**。很多模型蒙对答案，但中间推理是错的。

## 1.3MMLU vs GSM8K 对比（教程表格版）
|项目|MMLU|GSM8K|
|---|---|---|
|测试重点|多学科通识知识|多步数学逻辑推理|
|题型|4选1选择题|开放式应用题|
|主流评测方式|5‑shot|Zero/Few‑shot + CoT思维链|
|反映能力|知识面、记忆、阅读理解|分步推理、问题拆解|
|局限|难以考察长链条推理|仅小学数学，不代表高等数学|

> 核心结论：
> 传统单元测试、公开benchmark只能做参考；生产级大模型系统，必须构建面向自身业务的专属评估体系。

# 2评估完整生命周期：评估前置，贯穿全流程
传统软件流程：需求→开发→测试（开发结束之后做）→上线。
模型应用工程：**评估从需求阶段就启动，原型阶段就介入，上线之后持续运行，贯穿完整生命周期**。

| 项目阶段 | 评估核心目标 | 主要评估手段 |
|---|---|---|
| 需求分析阶段 | 定义什么叫“业务上合格的输出”，确定评估指标 | 业务专家参与，明确质量规约 |
| PoC原型阶段 | 快速验证想法，发现明显短板，不追求完备 | 人工主观评测、小批量样本 |
| 准生产阶段 | 构建离线评测集，搭建自动化回归流水线 | 离线评测集、AI‑as‑Judge、规则校验 |
| 大规模生产 | 监控线上真实业务表现，捕获真实BadCase | 线上抽样评估、用户反馈闭环、人在回路 |

> 重要原则：不要等到要上线的时候才开始写评测样本。评估是设计工作，不是测试工作。

### 3.2.1 区分三类指标：技术指标、业务指标、用户指标
在需求阶段，就要把模糊的“大模型回答要好”拆解为三类可衡量指标：
1. **技术指标（系统层）**
格式符合率、幻觉率、引用溯源正确率、工具调用成功率、拒绝有害请求成功率。
> 回答是否JSON格式正确；是否编造不存在文档；是否正确拒绝越权提问。

2. **业务指标（业务价值层）**
工单解决率、人工转接率、ROI、错误带来的业务损失下降幅度。
> 知识库客服：AI可以独立解决多少咨询，多少必须流转人工坐席。

3. **用户指标（用户价值层）**
用户点赞/点踩占比、会话放弃率、用户编辑修改模型输出的比例、用户满意度、信任度。

> 项目失败常见原因：只盯着技术指标，不去定义业务、用户指标。技术指标好看，但不能产生业务价值。

## 3.3 离线评估体系
离线评估，指不接入真实线上用户流量，使用固定评测数据集，自动化或者半自动化执行评估。是准生产阶段最重要质量闸门。

### 3.3.1 评测数据集由哪些样本构成
一份完备业务评测集，应当包含4类样本：
1. ✅正向标准样本：正常业务输入，预期得到合格回答；
2. 🧩边界Case样本：模糊提问、信息缺失、歧义问题；
3. ❌负向对抗样本：越权提问、prompt注入尝试、超出知识库范围提问；
4. 💥历史BadCase样本：线上曾经发生故障、产生幻觉的真实案例。

> 最佳实践：BadCase是评测集最高价值来源。每线上发现一个故障，整理成评测样本加入数据集，避免后续版本回归。

### 3.3.2 评测集数据来源
1. 业务专家人工编写（边界case、对抗case）
2. 历史真实业务日志脱敏抽取
3. 线上回流BadCase沉淀
4. 根据业务规约自动生成部分测试样本

⚠️注意：所有来自线上的样本，必须完成用户隐私脱敏，移除PII个人敏感信息。

### 3.3.3 评测集老化风险
业务会迭代更新：知识库文档修改、业务规则变更、政策更新。**旧的评测样本会失效，也就是评测集老化**。
> 现象：自动化评测全部通过，但是线上大量出错，因为评测集已经跟不上业务变化。

应对策略：
1. 评测集纳入版本管理，跟随业务迭代同步更新；
2. 定期从线上抽取新BadCase补充；
3. 每季度安排业务专家对评测样本做一轮审核清理。

### 3.3.4 离线评估核心质量维度
针对生成式业务，常用评估维度，可以作为AI‑Judge打分提示的维度：
- **事实一致性**：输出内容不能编造，必须和知识库/业务规约保持一致；
- **相关性**：回答和用户问题相关，不答非所问；
- **完整性**：覆盖用户问题需要的全部业务信息；
- **格式合规率**：严格输出JSON / Markdown等约定格式；
- **安全性**：正确拒绝越狱、越权、违规请求；
- **简洁度**：不冗余，不输出无关内容。

## 3.4 AI‑as‑Judge AI裁判模型评估实践
AI‑as‑Judge（裁判模型）：使用另外一个独立大模型充当“打分裁判”，对主模型输出结果做多维度评判打分，是现在工业界主流自动化评估手段。

> 注意：AI‑as‑Judge不是银弹，存在**自我评估偏差**，有明确适用边界。

### 3.4.1 适用场景与局限性
✅适合场景：
- 开放式文本质量打分（相关性、完整性、表达通顺度）；
- 大规模离线评测集批量打分，减少人工成本；

❌不适合完全单独使用的高风险场景：
金融、医疗、政务等高风险业务，不能把AI裁判结果当做最终判定依据。AI裁判本身也会幻觉、误判。

> 典型陷阱：Agent系统让Agent自己校验自己输出。属于严重反模式。裁判模型应当和业务主模型相互独立。

### 3.4.2 裁判Prompt设计要点
1. 清晰给出业务上下文、业务约束；
2. 明确打分维度，每个维度附带合格/不合格示例；
3. 要求裁判输出打分理由，而不是只输出分数，方便排查；
4. 优先输出结构化JSON结果，便于程序解析。

> 极简裁判Prompt示例
```
你是业务评测裁判。
【业务背景】企业内部知识库问答，回答必须严格参考参考文档，禁止编造信息。
输入用户问题：{{user_query}}
参考文档片段：{{reference_docs}}
待评测回答：{{model_output}}

请从下面3个维度打分，每个维度0‑10分，输出JSON：
1. fact_consistency：事实一致性，不能编造不在参考文档内的信息
2. relevance：回答与用户问题相关性
3. format_compliance：格式是否符合业务要求

同时输出reason字段，说明扣分原因。
```

### 3.4.3 制衡方案：混合评估策略
生产系统推荐**规则校验 + AI裁判 + 少量人工复核**三者结合：
1. 可以用代码规则判定的（JSON格式、关键字黑名单）优先交给代码，不消耗大模型；
2. 主观语义质量交给AI‑as‑Judge；
3. AI裁判给出低分样本，全部送入人工复核。

部分场景可以使用多个不同裁判模型交叉打分，降低单一个裁判的偏见。

## 3.5 线上评估与业务反馈闭环（第四阶段范式核心）
离线评测只能覆盖已经预见到的场景。真实用户会提出大量评测集没有覆盖的问题。必须依靠线上评估与反馈闭环持续收集真实世界信号。

反馈闭环链路：**用户行为信号采集 → 样本筛选 → BadCase沉淀 → 回流到提示词 / 知识库 / 评测集 / 微调数据集**。

### 3.5.1 两类反馈信号：显式反馈 & 隐式反馈
1. **显式反馈：用户主动操作**
点赞👍 / 点踩👎，用户手动编辑修改AI输出，主动报告错误。
> 优点：信号明确；缺点：大部分普通用户不会主动点击反馈按钮，样本量偏少。

2. **隐式反馈：挖掘用户行为埋点**
不需要用户主动点击，系统采集行为信号作为质量间接信号：
- 用户提问之后立刻重新提问；
- 连续多轮会话仍然没有解决问题；
- 直接转人工客服。

> ⚠️隐式反馈属于间接信号，不能直接判定回答错误，需要抽样人工复核确认。

### 3.5.2 线上抽样评估
线上全部流量送入人工评估成本太高，工业实践是**流量抽样**：按比例随机采样线上真实请求与应答，交由业务人员复核。
- 低风险业务：采样1‑5%流量；
- 高风险业务：提高采样比例；
- 重点关注被点踩、触发降级、工具调用失败的请求，对这类请求100%抽样复核。

### 3.5.3 反馈数据回流链路
收集得到BadCase之后，不能仅仅作为bug个案修复，要回流到系统四个位置：
1. **评测集**：把案例加入离线测试集，防止后续版本回归；
2. **提示模板**：如果错误来自提示词缺陷，迭代系统Prompt；
3. **知识库（RAG场景）**：知识缺失、知识错误，则更新文档、调整分块策略；
4. **微调数据集**：高频共性错误，评估是否加入微调训练集（微调是最后备选手段）。

> 这正是模型应用工程手段优先级：优先修改提示、知识库，微调后置。

## 3.6 评估流水线工程实现
把评估嵌入CI/CD流水线，每次改动Prompt、知识库、模型版本，自动运行离线评测集，输出评估报告。

### 3.6.1 CI集成离线回归流水线
触发条件：
- Prompt模板版本变更；
- 知识库大规模更新；
- 切换基座模型版本；

流水线动作：
1. 自动批量跑完整评测集；
2. 调用裁判模型或者规则引擎得到打分结果；
3. 输出评估报告：各个维度平均分、失败case明细；
4. 设置质量门禁：当事实一致性、格式合规率低于阈值，阻断发布上线。

> 注意：不要设置绝对100%通过门禁，大模型概率性特性允许少量可接受失败，设置业务可接受阈值（例如事实一致性≥92%）。

### 3.6.2 A/B测试与灰度评估
当有两套方案（版本A旧Prompt，版本B新Prompt），不直接全量发布，做灰度A/B分流。
- 一部分流量走旧版本，一部分流量走新版本；
- 对比两套版本离线+线上指标（幻觉率、用户点踩率、工具调用成功率）；
- 只有新版本指标显著优于旧版本，才全量切换。

## 3.7 本章常见反模式
1. **反模式1：只依赖公开Benchmark评估业务效果**
公开榜单不等于业务落地，必须自建业务评测集。

2. **反模式2：把AI‑Judge裁判模型当作100%可信真理**
裁判本身也会出错，高风险业务必须保留人工复核。

3. **反模式3：评测集一次性写完就不再维护，忽略评测集老化**
业务迭代，评测样本也要同步迭代更新。

4. **反模式4：收集BadCase，只修复个案，不回流评测集**
同一个缺陷后续修改代码、更换模型会再次复现，产生回归问题。

5. **反模式5：评估放在项目收尾阶段才做**
评估应该从需求阶段就介入定义质量标准。

6. **反模式6：完全依靠肉眼Demo主观判断质量，没有任何可复现评测集**
这是Vibe‑Coding原型思维，原型可以肉眼看，但准生产、生产系统必须有可复现评测。

## 3.8 实操练习
> 练习目标：为企业内部知识库问答场景，设计最小可用评测集。
1. 列出至少5条正向样本；
2. 设计3条边界case（信息不全、歧义提问）；
3. 设计2条对抗样本（超出知识库、prompt注入试探）；
4. 定义4个评估维度，写出对应的AI‑Judge裁判Prompt；
5. 设计反馈回流流程：当线上收到用户点踩之后，系统应当完成哪些动作。

## 3.9 本章小结
1. 大模型概率开放式输出，传统单元测试、公开Benchmark不足以保障业务质量，评估成为一等公民；
2. 评估贯穿全生命周期，分为需求定义指标、PoC人工评测、准生产离线自动化评估、线上抽样+反馈闭环；
3. 离线评测集包含正向、边界、负向、历史BadCase样本，需要持续维护，警惕评测集老化；
4. AI‑as‑Judge是强大工具，但存在误判，推荐规则+AI裁判+人工复核的混合模式；
5. 反馈闭环核心不是收集错误，而是把错误回流提示词、知识库、评测集，防止缺陷反复回归。
