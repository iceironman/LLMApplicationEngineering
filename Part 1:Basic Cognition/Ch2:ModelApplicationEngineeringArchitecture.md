**本章导读**
大模型应用工程并非一蹴而就，经历了从传统机器学习、提示原型、LLMOps，最终演进到模型应用工程范式成型的四个发展阶段。很多团队项目失败，根源在于混淆原型 Demo 与生产系统，把编排框架直接当作业务架构，缺少面向概率性大模型的整套系统设计思想。

本章从工程发展历史出发，讲解 Vibe‑Coding 原型开发模式的价值与风险，介绍 Agent 领域核心的 Harness（缰绳工程）思想；进一步从应用架构、数据架构、技术架构三个维度展开大模型特有的架构设计，同时覆盖多模型协作、高可用与容错体系，给出生产上线检查清单。理解本章内容，可以帮助你跳出 “调 Prompt、调框架” 的思维，建立面向可持续运营的 AI 系统架构思维。

读完本章你将理解：

- 模型应用工程四阶段演进脉络，对比传统机器学习、LLMOps 的差异；
- Vibe‑Coding 氛围编程的适用边界，厘清原型与生产系统的隔离原则；
- Harness 工程五大核心组件，分清模型、框架、运行时控制系统三者区别；
- 大模型应用在确定性、延迟、成本、安全层面区别于传统软件的架构特殊性；
- 应用 / 数据 / 技术三层架构的核心组件、数据流、存储选型与安全约束；
- 多模型协作的典型业务模式；
- 大模型系统特有的高可用、降级、容错设计思路，掌握生产上线检查要点。

**前置知识回顾**

1. 模型输出具备概率开放式特征，不以追求 100% 正确为目标，追求可控、可观测、错误可拦截；
2. 三层价值模型：技术价值、业务价值、用户价值，业务价值是系统建设的出发点；
3. 评估前置、业务反馈闭环是第四阶段模型应用工程的核心支柱。

# 1. 模型应用工程的发展历程
模型应用工程 (Model Application Engineering)：一门系统化地将基础模型 (Foundation Model) 能力转化为可用、可靠、可持续运营的应用系统的工程学科。核心研究命题：如何在真实业务场景中，将模型的概率性输出转化为稳定、可控、有商业价值的应用功能。模型应用工程并非凭空诞生，它脱胎于传统机器学习工程、MLOps，随着基础模型的普及逐步演化而来。核心范式发生重大反转：**传统机器学习工程：数据→模型→产品；模型应用工程：产品→数据→模型**。整个演进可以划分为四个阶段。

## 1.1阶段 1：传统机器学习工程时代（2012‑2020）

**核心范式：先训练模型，再交付产品**

- 业务模式：针对单一业务任务，采集标注数据，从零训练或者微调任务专用模型；例如风控、推荐、文本分类。
- 工程重心：**特征工程、数据集标注、模型训练、防止训练‑服务偏移**。MLOps 围绕模型训练、版本管理、模型部署展开。
- 系统特征：模型输出属于**封闭集合**，输出结果是有限类别，可使用传统单元测试、准确率、召回率做质量校验。
- 局限：每一个业务需求都要重新准备标注数据、重新训练模型；模型泛化能力有限，新增任务需要重做整套训练流程；无法处理开放式生成任务。

> 
> 这个阶段没有 “应用层适配” 的概念，工程的主要工作发生在**模型开发层**。

## 1.2阶段 2：提示工程原型时代（2020‑2022，GPT‑3 之后）

**核心范式：消费现成预训练大模型，依靠提示词完成任务**

- 标志性事件：GPT‑3 发布，证明强大预训练模型可以通过提示词完成大量任务，不需要修改模型权重。
- 工程重心：提示词设计、少样本 / 思维链；开发者直接调用模型 API，几乎不做训练。
- 系统特征：最简原型，输入提示，接收模型输出。快速做 PoC，几分钟即可做出演示 Demo。
- 暴露的现实痛点：幻觉、输出格式不稳定、业务私有知识缺失、提示注入攻击；仅靠提示词无法生产可用系统。
- 行业认知误区：一度认为 “只要写好 Prompt 就能解决业务问题”，忽视外围工程体系。

## 1.3阶段 3：LLM 应用工程 / LLMOps 时代（2022‑2024，ChatGPT 爆发）

**核心范式：提示词 + 外部上下文增强（RAG） + 简单微调，解决企业私有业务**

- 标志性事件：ChatGPT 发布，LangChain、LlamaIndex 等编排框架兴起，RAG 大规模落地，Agent 概念兴起。
- 工程重心：检索增强 RAG、提示模板管理、向量知识库、参数高效微调 LoRA、基础可观测。
- 系统特征：不再只依赖提示词；引入外部知识库补充模型知识；开始做输入输出防护、日志统计；企业大量做内部知识库问答系统。
- 新出现的工程难题：
  1. 模型输出是**概率开放式输出**，传统准确率指标失效，传统单元测试不足以保障质量；
  2. 幻觉、事实一致性、工具调用失败；
  3. Agent 带来 IO 阻塞、成本暴涨、不可控；
  4. 缺少标准化评估手段，通用公开 benchmark 和真实业务差距巨大。

> 
> 这一阶段 LLMOps 更多聚焦工具链，但是缺少一套完整面向业务的系统架构方法论，很多团队把框架当成架构本身。

## 1.4阶段 4：模型应用工程范式成型（2024 至今）

> 
> 参考《AI 工程：大模型应用开发实战》Chip Huyen 提出的工程思想：工具迭代很快，底层工程原则更加持久，重点关注如何把概率模型转化为可持续运营的业务系统。

**核心范式：演进式架构思想 + 全链路评估 + 业务反馈闭环 + 人在回路，面向生产可持续运营**

1. 重心上移到**应用开发层**，优先做应用层适配，微调是后置备选手段；手段优先级：提示工程 → RAG 上下文 → 结构化输出约束 → 数据增强 → 微调。
2. 明确区分原型 PoC、准生产、大规模生产系统；倡导**由简入繁演进式架构**，禁止一上来就搭建复杂 Agent 系统。
3. 评估成为一等公民：离线业务评测集、线上抽样评估、AI‑as‑Judge（AI 当裁判）评估流水线，评估贯穿整个生命周期。
4. 反馈闭环是系统持续迭代的核心：收集用户显式 / 隐式反馈，回流到提示、知识库、评测集、微调数据集。
5. 正视模型概率性本质：不以追求 100% 正确为目标，追求**可控、可观测、错误可拦截、错误可迭代**。
6. 完整三层技术栈：应用开发层、模型开发层、基础设施层；不再把 AI 工程等同于调模型或者调框架。

**和 LLMOps 的区别**

- LLMOps：偏向工具、运维、模型生命周期；
- **模型应用工程**：以业务价值为出发点，研究整套系统架构、组件演进、评估、反馈闭环，解决 “概率模型如何交付商业可用功能” 的核心命题。

## 2.2Vibe coding
### 2.2.1 什么是 Vibe‑Coding（氛围编程）
> 术语由 Andrej Karpathy 提出：开发者使用自然语言描述目标，交给大模型生成完整代码，依靠对话反馈即兴迭代；优先追求**快速跑通Demo、原型可演示**，弱化前置架构设计、规格文档、测试、可运维约束。

核心特征：
1. 以自然语言对话为主要开发接口，人输出意图，AI负责实现细节；
2. 即兴式迭代，没有完整前置规格、验收标准；
3. 适合PoC、Demo、创意验证；**天然不面向生产可持续运营**。

> [!NOTE]
> Vibe‑Coding ≠ AI辅助编程。AI辅助编程可以是严谨工程实践；Vibe‑Coding特指**无前置规格、即兴对话驱动的原型开发模式**。

### 2.2.2Vibe‑Coding 和模型应用工程的关系
回顾四阶段演进：
- 阶段2【提示工程原型时代】：只靠Prompt快速做Demo，忽视外围工程，大量PoC难以落地生产；
- 阶段3【LLM应用工程/LLMOps时代】：引入RAG、向量库、观测，但很多团队把框架当架构，原型直接上生产；
- 阶段4【模型应用工程范式成型】：核心目标：**把概率大模型，转化为可持续运营的业务系统**，强调演进式架构、全链路评估、业务反馈闭环、区分PoC/准生产/大规模生产。

**Vibe‑Coding 就是阶段2原型思维在代码层的延伸**：
1. ✅ 正向价值：**0‑1原型探索的强大工具**，快速验证想法，降低创意验证成本，快速产出PoC，适合想法验证阶段；
2. ⚠️ 核心冲突：Vibe‑Coding只解决“能不能跑出来”，**模型应用工程解决“能不能长期稳定运营”**；
3. ❌ 行业反模式：大量团队直接把Vibe‑Coding产出的原型直接上线生产，这是大模型项目失败的高频原因。

> [!IMPORTANT]
> 模型应用工程不排斥Vibe‑Coding做原型；但**坚决反对将Vibe‑Coding产出直接作为生产系统**。原型和生产系统必须做隔离、重构、补全工程约束。

|维度|Vibe‑Coding（氛围编程）|模型应用工程（阶段4范式）|
|---|---|---|
|核心目标|快速产出可运行Demo，验证想法|构建可持续运营、可迭代的业务系统|
|驱动方式|自然语言即兴对话，边做边想|前置规格、演进式架构、明确验收标准|
|评估|肉眼看效果，主观感受驱动|**评估为一等公民**：离线评测集、AI‑as‑Judge、线上抽样评估|
|反馈闭环|会话内临时反馈，会话结束丢失上下文|完整业务闭环：用户显式/隐式反馈回流提示词、知识库、评测集、数据集|
|对待模型概率性|忽略概率风险，追求“跑通即可”|正视概率本质：追求可控、可观测、错误可拦截、错误可迭代|
|产出物|PoC、Demo、演示原型|PoC / 准生产 / 大规模生产三级区分，演进式迭代|
|技术债|短期速度快，持续累积隐性技术债务|从设计阶段就考虑可维护性、可观测、安全、边界处理|
|适用阶段|仅原型探索阶段|覆盖原型→准生产→生产全生命周期|

### 2.2.3Vibe‑Coding 带来的典型工程风险（模型应用工程视角）
1. **架构漂移与上下文丢失**
对话会话结束，设计决策、取舍全部丢失；再次修改时AI大规模乱重构，系统腐化，出现“vibe‑coding宿醉”：前期开发飞快，后期维护成本指数级上涨。

2. **缺少可验证的评估体系**
只靠人肉眼判断效果，没有离线评测集、没有回归测试。大模型输出具备概率性，修改一处就引发隐性回归问题。

3. **安全与边界缺失**
AI生成代码经常省略输入校验、权限控制、异常处理，容易引入注入、密钥泄露等安全漏洞；很多边界case没有被覆盖。

4. **混淆原型与生产，跳过准生产阶段**
这是最常见反模式：Vibe产出的Demo直接上线，缺少观测、告警、错误拦截、业务反馈闭环。原型阶段的临时方案直接固化进生产系统。

5. **心智模型缺失，故障难以排查**
开发者不完全理解AI生成的内部逻辑；当大模型链路出问题，调试链路（RAG检索、工具调用、提示词）时，无法定位根因。

### 2.2.4模型应用工程下的正确使用范式：Vibe‑Coding 仅作为原型工具
遵循演进式架构思想：**原型快速探索 → 规格固化 → 工程加固，禁止原型直接投产**。完整工作流：
1. **PoC阶段：使用Vibe‑Coding快速探索**
用自然语言对话快速验证业务想法，产出可演示Demo；记录所有临时取舍、已知缺陷、待验证点。
> 输出物：可运行Demo，以及一份原型风险清单，明确哪些是临时实现。

2. **从原型沉淀规格文档（Spec）**
把验证有效的业务逻辑转化为：业务需求、验收标准、输入输出约束、失败案例、架构草图。
> 这一步是从Vibe‑Coding走向工程化的关键分界点。

3. **准生产阶段：按照模型应用工程范式重构**
- 应用层优先：提示词 → RAG上下文 → 结构化输出约束 → 数据增强 → 微调；
- 补齐可观测链路：日志、Trace、指标统计；
- 构建离线评测集，建立回归评估流水线；
- 补齐输入防护、异常降级、错误拦截；
- 搭建业务反馈闭环通路。

4. **大规模生产：全链路运维与持续迭代**
上线抽样评估、人在回路，业务反馈持续回流系统，持续迭代知识库、提示、评测集。

> 简单一句话总结：**Vibe‑Coding帮你快速看见可能性；模型应用工程帮你把可能性变成可以长期交付的业务系统**。

###一句话总结
> Vibe‑Coding是阶段2提示原型时代在代码开发侧的延续；阶段4模型应用工程范式，就是对Vibe‑Coding即兴原型模式的纠偏：保留原型快速探索的优势，增加规格、评估、反馈闭环、演进式架构，把概率模型系统带上生产。

## 2.3Harness工程
### 什么是 Harness Engineering
> 核心公式：**Agent = Model + Harness**；凡是不属于模型权重本身的外围系统，全部属于Harness范畴。
> Harness 本意是马的挽具、缰绳；**模型是“马”，具备强大生成能力，但没有边界、不懂环境约束；Harness就是整套控制系统，约束、引导、纠偏，让模型能力安全落地到真实业务系统**。

Anthropic 官方定义：Harness 提供**工具、知识系统、上下文管理、执行环境、权限、观测、反馈校验循环**，把原始大模型，转化为可执行任务的智能体系统。

Harness五大核心组件：
1. **Tools（工具）**：外部操作能力调用；
2. **Knowledge（知识）**：私有知识库、RAG检索、业务规约；
3. **Observation（观测）**：链路Trace、日志、执行结果采集；
4. **Action（行动接口）**：沙箱、执行环境、输出校验；
5. **Permissions（权限）**：安全边界、审批、隔离防护。

> [!NOTE]
> Harness Engineering不是提示工程，也不是上下文工程，是提示工程、上下文工程之上，完整运行时基础设施工程。
> - Prompt Engineering：写指令，单轮提示；
> - Context Engineering：管理送入模型的信息；
> - **Harness Engineering：管理完整执行循环、状态、安全、校验、错误恢复**。

### 2.3.1 Harness Engineering 和模型应用工程的关系
回顾本书四阶段：
- 阶段3（LLMOps时代）：大量团队聚焦模型、提示词、RAG组件，把LangChain/LlamaIndex框架直接当做完整架构；
- 阶段4（模型应用工程范式成型）：目标：**把概率大模型转化为可持续运营的业务系统**，完整三层栈：**应用开发层、模型开发层、基础设施层**，强调演进式架构、评估一等公民、业务反馈闭环、区分PoC/准生产/生产。

#### 1. 从属关系
**Harness Engineering 是模型应用工程在Agent/复杂大模型应用场景下的一套核心子范式、一套架构思想，不是完整全集。**
- 模型应用工程：覆盖全生命周期，包含基座选型、微调、数据治理、RAG、评估流水线、LLMOps运维、业务闭环，**覆盖普通LLM应用 + Agent智能体系统**。
- Harness Engineering：**聚焦Agent/多步骤复杂任务场景，重点解决模型外围运行时基础设施**；更偏向应用开发层与基础设施层，不包含底层模型微调、基座训练部分。

> 通俗理解：
> 模型应用工程 = 完整大模型业务系统工程方法论；
> Harness Engineering = 面向Agent场景下，“模型外面那套控制系统”的最佳实践子集。

#### 2. 理念高度对齐（核心共识）
两者底层工程哲学完全一致：
1. **模型只是系统的一个组件，不是系统全部**。业务稳定性问题绝大多数不出在模型权重，而出在模型外围的系统；不要一味调模型，优先改造外围系统。
2. **正视大模型概率本质**：不追求100%输出正确；通过外围约束、校验、观测、拦截，实现可控可运营。
3. **原型与生产必须严格区分**：Vibe‑Coding产出的Demo只是模型能力验证，缺少完整Harness的Agent绝对不能直接投产。
4. **手段优先级：上层优先，微调后置**。优先通过提示、上下文、工具、护栏、校验解决问题，微调作为最后备选。

#### 3. 差异点对比表（可直接放入文档）
|对比维度|模型应用工程（阶段4范式）|Harness Engineering（缰绳工程）|
|---|---|---|
|**适用范围**|全部大模型业务系统：简单问答、RAG、Agent、多轮对话等|**聚焦Agent/多步骤长链路智能体场景**|
|**覆盖范围**|完整三层栈：应用开发层、模型开发层、基础设施层；包含微调、数据集、基座管理、LLMOps运维|聚焦**模型外围运行时系统**；工具、记忆、权限、观测、执行循环；**不包含底层模型训练微调**|
|**核心目标**|构建可持续运营的企业业务系统，覆盖从PoC到大规模生产全链路|解决Agent系统的可靠性、安全性、长任务稳定性，约束模型行为|
|**评估体系**|离线评测集、AI‑as‑Judge、线上抽样评估、业务反馈闭环，全生命周期评估|重点聚焦Agent执行链路校验、工具调用校验、执行结果观测；偏向运行时校验|
|**来源**|Chip Huyen《AI Engineering》，行业落地沉淀|Anthropic、LangChain等团队，2026年Agent工业实践总结|
|**产出物**|完整业务系统、评测集、反馈闭环、LLMOps流水线|Agent运行时基础设施、工具编排、状态管理、安全护栏|

#### 4. 互补关系
1. **模型应用工程为Harness Engineering提供上层约束**
Harness只解决Agent运行时；模型应用工程提供完整业务视角：业务需求、评测集定义、业务反馈回流、运维SLA、成本治理，告诉Harness“要校验什么业务指标”。

2. **Harness Engineering补全模型应用工程在Agent场景的缺口**
传统模型应用工程更多围绕单轮调用、RAG问答；当进入多步骤、长周期、自主执行Agent场景，就需要引入Harness整套设计，解决状态丢失、工具调用失败、上下文溢出、自我评估偏差等问题。

> [!IMPORTANT]
> 模型应用工程 ≠ Harness Engineering。
> 如果业务只是简单RAG问答，不一定需要复杂Harness；一旦构建Agent、自主执行多步骤任务，Harness工程就成为生产落地的必要条件。

### 2.3.2Harness Engineering视角下的常见反模式（和模型应用工程踩坑点对齐）
1. **只调模型和Prompt，不做Harness层设计**
遇到Agent出错，反复修改提示词、更换更强基座，忽略工具校验、权限隔离、结果校验、状态管理。问题根源不在模型，而在外围控制系统缺失。

2. **直接把Vibe‑Coding生成Agent原型上线**
对话生成的Agent Demo，缺少完整Harness组件：没有沙盒、权限管控、执行校验、Trace观测，极易发生危险操作、不可控消耗。

3. **把框架（LangGraph等）等同于Harness**
框架只是基础组件库；Harness是基于组件之上的业务约束、权限、校验、评估闭环。很多团队直接使用框架默认配置上线，缺少业务化Harness设计，系统脆弱。

4. **过度依赖Agent自我评估**
Agent自己校验自己输出，会出现自我评估偏差；Harness工程提倡引入外部独立校验器、外部测试环境，和模型应用工程“评估作为一等公民”思想保持一致。

###2.3.3 在四阶段演进中的定位
- 阶段1：传统机器学习工程，MLOps，以模型训练层为核心；
- 阶段2：提示原型时代，Prompt，无外围系统；
- 阶段3：LLMOps时代，RAG、Agent框架兴起；**框架组件齐全，但缺少Harness完整运行时思想，很多团队直接把Demo投产**；
- 阶段4（模型应用工程范式成型）：
> Harness Engineering是阶段4在Agent领域的重要实践分支。当业务走向自主执行的智能体系统时，Harness就是模型应用工程思想在Agent上的具体落地。

### 2.3.4模型应用工程下Harness工程落地原则

> [!IMPORTANT]
> 在模型应用工程体系下使用Harness Engineering的落地原则：
> 1. Harness不是必选项：简单RAG问答场景，不需要构建复杂Agent Harness；
> 2. 演进式构建：从简单链路起步，不要一上来搭建复杂多Agent Harness；
> 3. 模型能力之外的可靠性，尽可能交给Harness（代码、校验、权限），而不是完全交给大模型提示词；
> 4. Harness必须配套完整的业务评测集、观测链路、业务反馈闭环，这部分属于模型应用工程范畴；
> 5. 禁止把缺少完整Harness约束的Agent原型直接上线生产。

# 3.模型应用工程中架构设计

## 3.1应用架构（组件、模式、业务逻辑、交互、流转）
应用架构聚焦：系统组件定义、组件之间接口与交互逻辑、业务处理流程、架构模式、业务容错、用户交互编排。
### 3.1.1模型应用架构的本质特殊性

|维度|传统软件架构|模型应用架构|
|---|---|---|
|确定性|相同输入 → 相同输出|**非确定性**，相同输入可得到不同输出；temperature=0也会因模型版本发生行为漂移|
|延迟特征|毫秒级（10‑100ms）|秒级（1‑30s）；流式输出成为必备体验|
|成本模型|服务器实例，固定成本|**按Token可变计费**；调用量、输入输出长度直接决定账单|
|版本与行为|代码即逻辑，行为完全可控|模型更新带来行为漂移，业务逻辑一部分存在于模型权重|
|质量保障|单元测试、集成测试，二元对错判断|多维评估 + 持续线上监控，输出质量是程度性而非非黑即白|
|安全边界|边界清晰，防范传统漏洞|边界模糊动态，需要防护Prompt注入、越狱、工具越权|

连锁影响简述：
1. **非确定性**：传统断言测试失效，不能无脑重试，需要语义缓存、降级兜底；
2. **高延迟**：流式SSE/WebSocket、异步长任务、TTFT作为核心指标；
3. **可变Token成本**：路由分流、缓存、Prompt治理、预算管控成为硬性工程要求；
4. **特有安全威胁**：Prompt注入、越狱、工具越权，安全需要前置嵌入架构链路。

---

### 3.1.2五种应用架构模式
1. **直连模式**：应用后端直接调用模型API。适合PoC原型、Vibe‑Coding快速Demo；缺少网关、缓存、熔断，禁止企业直接生产使用。
2. **网关模式**：应用后端 → 模型API网关 → 多模型后端。企业级标配；网关作为统一抽象层，承担路由、限流、重试、缓存、计量。
3. **RAG增强模式**：应用后端 + 向量检索 + 大模型。面向知识密集场景，私有知识库补充模型能力，降低幻觉。
4. **Agent模式**：应用后端 + Agent推理引擎 + 工具集。用于多步骤自主任务。
> [!IMPORTANT]
> Agent = Model + Harness。模型负责推理；**Harness属于应用架构层**，包含状态管理、工具权限控制、执行校验、错误恢复；LangChain/LangGraph只是组件库，不等于完整Harness应用架构。
5. **混合模式（生产主流）**：网关路由层根据请求意图，分发到缓存/小模型直连/RAG/Agent不同链路；全部链路输出统一经过安全校验返回。

### 3.1.3核心应用组件与交互逻辑
- **模型路由组件**：按成本、能力、延迟、租户做流量分发；支持A/B灰度。
- **语义缓存组件**：基于向量相似度命中历史结果，降低调用量。
- **多模型协作编排组件**
    1. 分级处理：小模型意图分类，简单请求直答，复杂请求递交大模型；
    2. 校验链：生成模型 + 独立校验模型，降低幻觉；
    3. 裁判模型(Judge‑Model)：AI‑as‑Judge评估打分；
    4. 分层生成：小模型生成草稿，大模型精加工；
    5. 流水线串联：意图识别 → 检索 → 生成 → 安全过滤 → 格式校验。
- **流式交互组件**
    - SSE：单向HTTP流式，适用于一问一答对话；
    - WebSocket：全双工，支持中途停止、修改指令，适用于Agent长会话；
    - 核心指标TTFT（首Token到达时间）；支持客户端中止请求，释放模型调用避免浪费Token。
- **会话与状态管理组件**
    - 显式有限状态机：适合流程固定业务（工单、表单）；
    - 模型驱动隐状态：开放对话；工程最佳实践：关键节点使用显式规则约束。
- **反馈闭环组件（阶段4范式核心）**
    - 显式反馈：点赞/点踩；
    - 隐式反馈：用户编辑、重新提问等行为信号；
    - 回流链路：反馈数据回流评测集、提示模板、知识库迭代。
- **容错与降级组件**
    - 指数退避重试：非幂等生成场景谨慎开启；
    - 断路器模式：错误率触达阈值切换备用模型，防止雪崩；
    - 分层降级：主模型→备用模型→轻量模型→缓存结果→友好兜底提示/人工入口。

### 3.1.4应用架构选型：单体 vs 微服务、事件驱动
1. **单体应用架构**：RAG、Agent、模型调用全部在同一进程。适合PoC、内部工具、小规模业务。
2. **微服务应用架构**：意图分类、RAG检索、Agent、模型网关拆分为独立服务。
> 选型原则：**从单体起步，避免过早微服务；出现性能瓶颈再拆分；优先独立模型网关，再拆分RAG、Agent**；适合日均十万调用、多团队企业业务。
3. **消息队列 / 事件驱动应用模式**
    - 异步长任务：提交任务返回TaskId，后台消费处理；
    - 削峰填谷，解耦各个业务环节；新增链路无需修改原有业务代码。

### 3.1.5AI系统特有技术债务（应用层）
1. Prompt碎片化：提示词散落在代码，无版本管理；解决方案：中心化Prompt注册表，纳入版本评审。
2. 模型强依赖锁定：业务硬编码适配单一模型；解决方案：网关抽象层，提示与模型解耦，定期做多模型切换演练。

## 3.2数据架构（数据对象、数据流、存储、生命周期、数据安全）
> 数据架构聚焦：有哪些数据、数据如何流动、存储选型、数据生命周期、脱敏加密、数据合规。

### 3.2.1核心数据对象
1. **知识库原始文档 & 分块片段**：业务私有知识，RAG数据源；
2. **向量Embedding数据**：文档向量、用户Query向量，用于检索、语义缓存；
3. **会话数据**：对话历史、会话状态、用户画像、意图参数；
4. **缓存数据**：语义缓存、精确缓存；
5. **评测数据集**：离线评测样本、BadCase样本，用于迭代系统；
6. **审计日志&链路采样数据**：调用记录、Trace采样（禁止完整存储Prompt/Reply原始报文）；
7. **Prompt模板、配置元数据**：提示模板、路由规则、阈值配置。

### 3.2.2关键数据流
1. **RAG数据流**：文档摄入 → 文档分块 → Embedding生成 → 写入向量库 → 用户Query向量化 → 相似度检索 → 拼接上下文送入大模型；
2. **会话数据流**：用户输入 → 会话状态读取更新 → 业务链路处理 → 结果返回 → 用户反馈采集 → 反馈回流评测集/知识库；
3. **缓存数据流**：用户请求Embedding生成 → 向量库相似度检索；命中直接返回缓存，未命中调用模型，成功结果写入缓存并设置TTL过期。

### 3.2.3存储选型
|数据类型|推荐存储|
|---|---|
|向量检索、语义缓存向量|小规模Redis向量扩展；大规模 Milvus / Pinecone 向量数据库|
|会话、工单、审计元数据、业务配置|PostgreSQL等关系型数据库|
|临时缓存、计数|Redis|
|原始文档、冷归档数据|对象存储|

### 3.2.3数据安全与生命周期
1. **敏感数据脱敏**：身份证、银行卡、业务隐私信息在入库、检索输出两层脱敏；
2. **PII隐私保护**：日志只记录哈希/采样，禁止完整存储用户Prompt和返回内容；
3. **生命周期管理**：向量库增量更新，缓存TTL过期；会话冷数据归档；评测集定期更新迭代；
4. **评测集老化风险**：业务演进会导致旧评测样本失效；需要定期将生产BadCase补充进评测集。

## 3.3技术架构（基础设施、中间件、部署、可观测、安全底座）
> 技术架构聚焦：底层软硬件基础设施、中间件平台、部署编排、网络、可观测、安全基础设施、运维能力。

### 3.3.1基础设施与部署平台
1. **容器化Docker**
    - 代码与模型文件分离挂载，避免镜像臃肿；
    - 密钥、配置通过环境变量/密钥管理注入，禁止硬编码；使用非root账号运行。
2. **Kubernetes编排**
    - Deployment无状态部署，HPA水平自动扩缩容；
    - GPU资源声明，用于私有化本地模型推理；
    - Secret管理密钥；Service/Inges提供网络访问；
    - 私有化模型支持蓝绿/金丝雀发布。
3. **模型服务形态**
    - 公有云第三方模型API；
    - 私有化自托管大模型推理服务。

### 3.3.2中间件组件
1. **模型网关中间件**：统一路由、限流、重试、断路器、Token计量、多供应商切换（开源参考 LiteLLM）；
2. **消息中间件**：Redis Stream / RabbitMQ / Kafka；用于异步任务、事件驱动、削峰填谷。

### 3.3.3可观测技术底座：Traces / Metrics / Logs
1. **Trace链路追踪**：trace_id串联一次请求下全部模型调用、检索、工具调用；记录TTFT、各环节耗时，定位幻觉、超时故障。
2. **Metrics指标**
    - 通用指标：QPS、P99延迟、错误率；
    - 大模型特有指标：输入输出Token统计、估算成本、缓存命中率、各模型流量占比、断路器/降级触发次数。
3. **结构化日志**：记录`request_id、user_id、model_id、token_count、latency`；敏感报文哈希采样。
4. **告警策略**：错误率突增、延迟恶化、预算超限、缓存命中率暴跌、降级频繁触发。

### 3.3.4安全技术基础设施
1. **身份认证授权**：对外JWT/OAuth2；内部服务mTLS、内部API密钥；
2. **传输&存储加密**：TLS1.2+传输加密；敏感数据库字段加密；KMS密钥管理；
3. **审计底座**：防篡改审计日志，满足合规留存期；
4. **网络层防护**：限流防攻击、IP黑白名单。

### 3.3.5成本治理（技术架构运维能力）
1. 网关层实现模型路由降本；
2. 预算管控：按租户设置Token/金额上限，超阈值告警、限流降级；
3. 成本报表，按模型、接口、租户做成本分解。

# 4.多模型协作架构
复杂的AI应用往往不是一个模型能搞定的,需要多个模型各司其职、协作完成。
- 场景一：分级处理。用小模型作第一轮意图分类和简单回答，只将复杂请求升级到大模型。既降低成本，又减少大模型的负载。
- 场景二：校验链。用模型A生成答案，用模型B校验答案的准确性和安全性。双模型交叉校验可显著降低幻觉率。
- 场景三：能力互补。用专长模型处理专长任务——代码分析用Claude Opus4.6,多模态理解用Gemini 3.1 Pro,中文报告生成用Qwen3-Max。
- 场景四：裁判模型(Judge Model)。用独立模型对主模型的输出进行评分或裁决例如：主模型生成多个候选回答，裁判模型从相关性、安全性、事实准确性等维度打分，选择最优输出；或在多Agent辩论场景中，裁判模型判定哪方论证更有说服力。裁判模型通常选用推理能力强、偏见较小的模型，与主模型形成制衡。
- 场景五：分层生成(Layered Generation)。先由小模型生成草稿或大纲，再由大模型进行润色、扩写或深化。适用于长文生成、报告撰写等场景——既控制成本(大模型只处理“精加工”环节),又保证最终质量。
- 场景六：能力互补组合。将不同专长模型串联为流水线：如“意图识别(小模型一知识检索(RAG)→答案生成(中模型)→安全过滤(小模型)→格式校验(规则引擎)”。每个环节由最合适的模型或组件负责，整体效果与成本达到最优平衡。

多模型协作可按“先分流、后汇合”实现：先用小模型作意图分类，再将请求路由环同能力链路，最终统一经过安全校验后返回结果。

# 5.高可用于容错设计

模型应用大量依赖外部模型API，具备**非确定性输出、秒级~数十秒级长延迟、按Token计费、输出存在幻觉等软故障**，它的容错逻辑与传统业务系统存在显著区别。传统系统容错重点解决进程崩溃、网络故障；而模型应用除硬件、网络故障外，还需要处理服务商限流、模型服务抖动、输出质量不达标、流式中断、重试带来结果不一致等特有问题。

高可用容错整体分为三层：**业务/架构层、服务/路由层、链路/网络层**。
- 业务架构层解决供应商冗余、模型降级；
- 服务路由层负责断路器熔断、流式中断处理；
- 链路网络层处理超时、指数退避重试。三层协同完成故障检测、故障隔离、自动切换、优雅降级与可观测告警。

## 5.1业务/架构层容错设计
业务架构层从业务拓扑层面消除单点依赖，核心手段为**多供应商冗余**和**分层模型降级策略**。

### 5.1.1 多供应商冗余
不要将全部业务流量绑定单一模型服务商。核心业务至少对接两家以上模型供应商，当主服务商发生大面积故障，系统自动切换至备用服务商，避免整体业务瘫痪。

**供应商选型评估要点**
1. 地域分布：优先选择不同地域机房的服务商，规避单区域故障。
2. 能力等效性：备用模型需要满足业务核心效果指标，不能出现能力断崖式下跌。
3. 成本可控：降级切换后会带来成本波动，需要评估预算上限，防止账单暴涨。

> 如果是私有化部署本地模型，则遵循传统微服务高可用方案：多实例无状态部署、负载均衡、健康检查、滚动更新与蓝绿发布；公有云API模式的高可用能力，主要依靠多供应商快速切换实现。

### 5.1.2分层容灾降级策略（L1~L4四级降级）
降级不等于简单换一个模型，需要设计逐级回落的完整链路，每一级都有明确的触发条件与输出形态，保证尽可能对外提供服务，极端情况下也要给出友好提示，不能直接抛出错误堆栈。

- **L1降级（模型级切换）**：主模型不可用（超时、限流、服务报错），切换到同能力备用模型。
- **L2降级（能力降级）**：备用模型同样故障，切换至轻量小模型，牺牲部分推理能力，优先保障可用性。
- **L3降级（缓存兜底）**：全部模型服务不可用时，返回匹配的语义缓存结果。
- **L4降级（人工/提示兜底）**：缓存无匹配结果，返回友好业务提示，预留人工接管入口。

降级链路示例：
> 主旗舰模型 → 备用旗舰模型 → 轻量高速模型 → 缓存结果 → 提示“服务暂时繁忙，请稍后重试”

> ⚠️注意：降级策略上线前必须完整测试，验证每一级链路是否可以正常触发、返回内容是否符合业务预期，不能只做编码不做故障演练。

##  5.2服务/路由层容错设计
服务路由层一般实现在**API模型网关**内部，核心组件为**断路器模式、流式响应中断处理与恢复**，负责故障隔离、阻止故障向上游扩散，同时适配模型特有的流式输出场景。

### 5.2.1断路器模式 Circuit Breaker
模型API经常出现短时间批量报错，如果不停向故障服务发送请求，会造成请求堆积、雪崩效应，同时消耗大量无效Token成本。断路器实现故障隔离，状态分为关闭、打开、半开三种状态。

1. **关闭状态（Closed）**：正常工作，流量正常转发到模型服务；持续统计调用失败率。
2. **打开状态（Open）**：当调用错误率超过阈值（例如50%，或连续5次调用失败），断路器打开；不再转发请求至故障模型，直接触发降级逻辑。
3. **半开状态（Half‑Open）**：经过冷却时间（例如30秒）后进入半开；少量试探流量转发到故障模型；如果调用成功，恢复关闭状态；调用失败，重新切回打开状态。

工程要点：
- 断路器需要记录完整日志与监控指标，记录状态切换事件，便于运维排查故障。
- 需要区分错误类型：429限流、5xx服务错误计入失败计数；业务参数错误400不应当计入熔断失败。

### 5.2.2流式响应的中断处理与恢复
模型应用大量使用SSE流式输出，传统HTTP错误处理不完全适配流式场景。流式链路的故障发生在数据传输中途，此时HTTP状态码仍然是200 OK，但是流中途断开。

流式容错工程实践：
1. 客户端支持中途终止请求，用户点击停止生成时，客户端发送Abort信号；服务端同步终止上游模型API调用，避免继续消耗Token产生无效成本。
2. 流传输中途发生超时、网络断开，向前端推送专门错误事件，前端展示友好提示，禁止页面卡死、白屏。
3. 支持断点续传可选：会话保存已经生成的片段，中断后用户重试时，可把已输出内容复用，不需要全部重新生成。

##  5.3链路/网络层容错设计
链路网络层处理单次模型调用的底层网络异常，主要包含**分层超时设计、指数退避重试与随机抖动**。模型API延迟可达1‑30秒，传统3秒超时、简单固定间隔重试方案完全不适用。

### 5.3.1分层超时设计
不能设置单一统一超时值，区分连接超时、读取超时、整体任务超时，防止误杀正常长生成任务，同时阻止无限阻塞。
1. **连接超时**：建立网络连接的最大时间（一般5秒），连接无法建立直接快速失败。
2. **读取超时（流超时）**：两次Token分片之间最大间隔，用于识别流式卡住无输出。
3. **全局任务总超时**：整个请求最大生命期，兜底保护，防止Agent长任务无限循环。

> 业务参考配置示例：连接超时5s，分片读取超时10s，全局总超时60s；不同业务场景需要结合P99延迟做调整。

### 5.3.2指数退避重试策略
针对瞬时故障（网络抖动、429限流、服务短暂5xx报错）使用指数退避重试：第1次失败等待1s，第2次等待2s，第3次等待4s，以此类推；最大重试次数建议设置3‑5次，同时增加随机抖动，防止大量请求同时重试产生惊群效应。

**重要约束（模型场景独有）**
1. 模型生成属于**非幂等调用**，相同输入多次重试，返回输出结果可能不一样；不能无脑全部开启自动重试。
2. 对于业务不允许输出结果变化的场景，应当关闭自动重试，或者增加幂等键设计。
3. 客户端参数错误、Prompt格式错误这类业务错误，禁止重试。

## 5.4 高可用配套：模型应用可观测性架构
高可用离不开完整可观测体系，传统监控只能捕获进程崩溃这类硬故障；模型应用还需要识别“HTTP返回200，但回答质量错误”这类软故障。可观测由Trace链路追踪、Metrics指标、Logs结构化日志三部分组成。

### 5.4.1Trace（链路追踪）
一次用户请求可能串联多次模型调用（意图分类、RAG检索、Agent多轮工具调用、安全校验），需要全链路传递trace_id，把同一个会话的所有调用串联起来。
需要记录关键时间指标：请求发出时间、首Token到达时间TTFT、流结束时间，用于分析流式体验。

### 5.4.2Metrics核心监控指标
除QPS、延迟P95/P99、错误率通用指标外，模型应用特有指标：
- Token消耗统计：输入、输出Token，按模型、租户、接口维度聚合
- 成本估算指标
- 模型路由流量分布占比
- 缓存命中率（精确缓存、语义缓存）
- 故障事件统计：降级触发次数、断路器打开次数、重试次数

### 5.4.3Logs结构化日志
日志字段至少包含：`request_id`、`user_id`、`model_id`、`token_count`、`latency`、`cost_estimate`。
> 安全规范：禁止完整记录Prompt和回答原文，防止用户敏感PII泄露；可记录哈希摘要用于审计排错。

### 5.4.4告警策略
重点告警项：
1. 接口错误率突增
2. P99延迟超出阈值
3. Token消耗与成本超预算
4. 缓存命中率大幅下降
5. 降级、断路器打开事件突增

##  5.6常见误区总结
1. **误区1：依赖大量重试提升成功率**。模型调用非幂等，重试会带来输出结果不一致，同时放大Token成本；只对网络瞬时故障开启有限次数重试。
2. **误区2：只关注HTTP错误码，忽略流式中途故障与输出质量软故障**。状态码200不代表业务成功，流式中断、幻觉属于模型特有故障，必须纳入容错体系。
3. **误区3：降级只切换模型，缺少完整兜底链路**。全部模型挂掉后必须有缓存、人工入口、友好提示，不能直接抛出异常。
4. **误区4：只编码不做故障演练**。熔断、降级逻辑只有模拟故障才能验证是否真正生效。
